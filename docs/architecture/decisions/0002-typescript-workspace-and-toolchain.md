- Status: accepted

- Decision owners: GitBlocks maintainers
- Governing issue:
  [#3 — Phase 1: Establish the TypeScript workspace and verification pipeline](https://github.com/kgudipati/gitblocks/issues/3)

## Context

GitBlocks has product, architecture, security, testing, reliability, repository,
and planning policy but no executable workspace or automated verification.
Before later product code can land, the development standards require a stack
decision for the runtime, language/module semantics, package manager,
formatter, linter, compiler strictness, tests, dependency boundaries,
supply-chain controls, generated code, and exact local/CI commands.

This decision establishes that engineering system without selecting a product
framework or implementing a product service. The only executable package is
private repository-policy tooling. Repository content remains untrusted data
and is never executed merely because the tooling scans it.

## Decision

### Runtime support policy and current pin

GitBlocks supports the Node.js 24 LTS major line from `24.12.0` inclusive and
excludes Node 25 and 26. Node 24.12.0 is the minimum because Node's built-in
TypeScript type stripping became stable there. Production applications should
use an LTS release, and Node 24 is the issue-approved LTS line.

The current repository pin is Node `24.18.0`, the latest Node 24 LTS patch
verified on 2026-07-28. `.node-version` and CI use that patch. The root engine
contract is `>=24.12.0 <25`, and pnpm checks dependency engines against the
minimum supported runtime so a contributor on 24.12.x is not given a graph that
only works on a later patch.

The major-line/minimum policy is durable. The exact patch pin is replaceable
through an ordinary reviewed dependency/toolchain update and is not an eternal
architecture choice.

Primary references:

- [Node.js release status](https://nodejs.org/en/about/previous-releases)
- [Node.js 24.18.0 LTS release](https://nodejs.org/en/blog/release/v24.18.0)
- [Node.js native TypeScript support](https://nodejs.org/api/typescript.html)

### Package manager, workspace, and exact updates

pnpm 11 is the only supported package manager. The current exact pin is
`pnpm@11.17.0` through the root `packageManager` field. The lockfile is
committed and generated by pnpm; contributors and agents must not hand-edit it.
All direct dependency specifiers are exact, with no caret, tilde, dist-tag, Git,
or tarball selector.

The workspace reserves `apps/*`, `packages/*`, and `tools/*` for future owned
packages but creates only `tools/repository-checks` now. Reserved globs do not
justify empty directories or placeholder applications. pnpm recursive/filter
scripts provide orchestration until measured workspace size or CI timing
demonstrates a need for a task runner.

Dependency updates arrive through reviewed pull requests. Dependabot checks the
npm/pnpm manifests and GitHub Actions weekly, groups compatible non-major
development-tool updates where useful, and leaves major updates independently
reviewable. Updates never auto-merge.

Primary references:

- [pnpm installation](https://pnpm.io/installation)
- [pnpm workspace settings](https://pnpm.io/settings)
- [pnpm supply-chain guidance](https://pnpm.io/supply-chain-security)
- [GitHub Dependabot configuration](https://docs.github.com/en/code-security/concepts/supply-chain-security/about-the-dependabot-yml-file)

### Language and module semantics

Owned TypeScript intentionally uses the stable TypeScript 6.0 compatibility
and compiler-API line; the current pin is `6.0.3`. TypeScript 7.0 is now stable,
but it does not currently ship a compiler API. The current stable
`typescript-eslint` line officially supports TypeScript `>=4.8.4 <6.1.0`, and
GitBlocks requires its compiler API for typed ESLint rules. TypeScript documents
a side-by-side transition using TypeScript 7 plus a TypeScript 6
compatibility/API package, but two compiler toolchains and package aliases
would add install, configuration, diagnosis, and update complexity without
current product value. GitBlocks therefore remains on TypeScript 6.0.3 for this
phase.

Owned JavaScript and TypeScript are ECMAScript modules with NodeNext module and
resolution semantics. Relative import specifiers include extensions. Runtime
path aliases that require rewriting are prohibited; workspace package exports
and relative imports are the supported boundaries.

Compiler policy explicitly enables:

- `strict`;
- `noUncheckedIndexedAccess`;
- `exactOptionalPropertyTypes`;
- `noImplicitOverride`;
- `noFallthroughCasesInSwitch`;
- `noPropertyAccessFromIndexSignature`;
- `useUnknownInCatchVariables`;
- `forceConsistentCasingInFileNames`;
- `verbatimModuleSyntax`;
- `isolatedModules`;
- `erasableSyntaxOnly`;
- `rewriteRelativeImportExtensions`;
- NodeNext module and resolution semantics; and
- explicit target, library, declaration, emit, source-map, and incremental
  behavior.

TypeScript 6's changed defaults are still written explicitly where they are
part of the GitBlocks contract. The code does not use enums, runtime
namespaces, parameter properties, decorators, import aliases, or other syntax
that Node's type stripper would need to transform.

Primary reference:

- [TypeScript 6.0 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html)
- [TypeScript 7.0 announcement and compiler-API transition](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)
- [typescript-eslint supported dependency versions](https://typescript-eslint.io/users/dependency-versions/)

### Native TypeScript stripping and emitted output

Node's native type stripping is allowed only for repository-owned tooling that:

- runs on the supported Node 24.12+ runtime;
- uses erasable syntax enforced by the compiler;
- has no path-alias or transform requirement;
- stays outside `node_modules`; and
- is invoked from reviewed repository scripts.

The repository-check CLI may run its TypeScript source directly for local
checks and tests. Type checking remains a separate required command because
Node strips types without checking them.

TypeScript also emits ESM JavaScript, declarations, and source maps for the
private workspace package. Any future package or service that is executed or
distributed through a workspace package boundary must consume emitted
JavaScript through declared exports rather than depend on Node stripping
TypeScript under `node_modules`. Source imports use `.ts` extensions and the
compiler rewrites them to `.js` during emit.

### Formatting and linting

Prettier is the sole mechanical formatter for supported TypeScript, JavaScript,
JSON, YAML, and Markdown text. The current pin is `3.9.6`.
`format:check` is read-only and `format` may modify files.

ESLint uses the flat configuration format with:

- ESLint `10.8.0`;
- `@eslint/js` `10.0.1`;
- `typescript-eslint` `8.65.0`; and
- `eslint-config-prettier` `10.1.8`.

`typescript-eslint` explicitly supports ESLint 10 and TypeScript versions
`>=4.8.4 <6.1.0`. Typed linting uses the TypeScript project service and strict
type-checked rules. Promise safety, safe error handling, exhaustive switches,
and unused-disable reporting are errors. Scoped test/config rules address their
different environment without globally weakening production/tool source
rules. `onUnsupportedTypeScriptVersion: 'error'` makes lint fail if a future
TypeScript update leaves the officially supported range instead of emitting
only a warning. CI permits zero warnings.

Prettier owns formatting; ESLint owns correctness and semantic rules.
`eslint-config-prettier` disables rule conflicts rather than duplicating
format policy.

Primary references:

- [typescript-eslint supported dependency versions](https://typescript-eslint.io/users/dependency-versions/)
- [typescript-eslint typed linting](https://typescript-eslint.io/getting-started/typed-linting/)
- [Prettier documentation](https://prettier.io/docs/)

### Testing and coverage

Vitest 4 stable is the test runner; the current `vitest` and
`@vitest/coverage-v8` pins are both `4.1.10`. Vitest 5 beta and every other
prerelease line are excluded. Native V8 coverage provides the initial measured
baseline.

Tests are deterministic and isolated: controlled temporary directories, no
live network, arbitrary sleeps, global Git configuration, credential, or
filesystem-order assumptions. Unit tests cover pure validators; integration
tests cover the real filesystem and CLI boundary. Security-sensitive parsers
and paths include negative and abuse cases. Coverage is recorded but no
repository-wide threshold is introduced until a representative baseline and
critical gaps are reviewed under the testing policy.

The review-corrected Phase 1 baseline is 86.17% statements, 83.77% branches,
98.48% functions, and 85.98% lines across the pure policy and repository
boundary modules. The CLI and re-export entry point are exercised through
subprocess tests and intentionally excluded from line-percentage accounting.

Primary references:

- [Vitest guide](https://vitest.dev/guide/)
- [Vitest V8 coverage](https://vitest.dev/guide/coverage)

### Architecture enforcement

dependency-cruiser `18.1.0` enforces:

- no circular runtime dependencies;
- no unresolved imports;
- no production source importing tests;
- no production source importing undeclared or development-only dependencies;
- no deep imports across future workspace package boundaries;
- adapters/transports may depend toward application and domain layers, never
  outward in the opposite direction, when those paths exist; and
- future product domain/application code may not import repository tool code.

Rules for future paths are dormant until files exist and do not require empty
directories. Positive and negative fixtures prove the critical rule behavior.

Primary reference:

- [dependency-cruiser rules reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md)

### Repository-policy tooling

`@gitblocks/repository-checks` is a private, non-product package. It owns
bounded, typed validation of current branch, PR title, GitHub workflow,
Markdown link, and repository invariant policies. Pure validators accept
explicit input and return typed diagnostics. Filesystem, process, root
resolution, and CLI exit behavior remain boundary adapters.

The CLI uses stable exit categories for success, policy violation, usage error,
and tool/internal failure. Traversal and diagnostics are sorted and bounded.
Paths are normalized and contained; symlink escape is rejected. YAML and
Markdown are parsed without execution using:

- `yaml@2.9.0`;
- `mdast-util-from-markdown@2.0.3`; and
- `github-slugger@2.0.0`.

Repository source, documentation, metadata, workflow text, paths, and parser
output are untrusted data. The tool never runs or constructs a shell command
from them; never installs, builds, evaluates, or dynamically imports them; and
never uses `eval`, `Function`, executable YAML schemas, or active Markdown
rendering. Diagnostics do not print file bodies or matched secret values.

### Secret and dependency security

Secretlint `13.0.4` with
`@secretlint/secretlint-rule-preset-recommend@13.0.4` scans tracked source and
documentation locally and in CI. Secretlint masks secret values by default.
The configuration never opts into unmasked output. Ignore rules are minimal
and cannot hide source or fixtures merely for convenience.

`pnpm security:audit` performs the online registry vulnerability audit.
`verify` remains deterministic without credentials or live provider/network
tests and includes the local secret scan. `verify:ci` adds the online audit and
fails if the registry is unavailable; no `|| true`, conditional skip, or
failure suppression is permitted.

Primary references:

- [Secretlint documentation](https://github.com/secretlint/secretlint)
- [Secretlint 13.0.4 release](https://github.com/secretlint/secretlint/releases/tag/v13.0.4)

### Software-supply-chain controls

pnpm configuration makes these controls explicit:

- exact `packageManager` and dependency versions;
- frozen lockfile in CI and documented local validation;
- `strictPeerDependencies: true`;
- `autoInstallPeers: false`;
- `engineStrict: true`, evaluated against Node 24.12.0;
- `strictDepBuilds: true` and an explicit `allowBuilds` map, so dependency
  lifecycle/build scripts are denied unless reviewed;
- `dangerouslyAllowAllBuilds: false`;
- `blockExoticSubdeps: true`;
- `minimumReleaseAge: 1440`;
- `minimumReleaseAgeStrict: true`;
- `minimumReleaseAgeIgnoreMissingTime: false`;
- `trustPolicy: no-downgrade`, with only a bounded old-package policy or exact
  evidence-backed exception if the resolved graph requires it; and
- `trustLockfile: false`, so a committed lockfile does not bypass configured
  release-age and trust verification.

Any build allowlist or trust exception identifies the exact package/version,
purpose, behavior, provenance, risk, owner, and review evidence in this ADR and
the execution plan. The final resolved graph determines whether an exception is
needed; the default is none.

The Phase 1 resolution requires no exception: `allowBuilds` is empty and no
trust-policy exclusion exists. The lockfile has 325 package records and 325
snapshots, all with SHA-512 integrity and none with an exotic source,
prerelease, or `requiresBuild` marker. A manifest review of all 295 package
versions installed on the validation platform found no `preinstall`, `install`,
or `postinstall` script.

All selected direct packages use Apache-2.0, MIT, or ISC licenses, identify an
official project repository, provide npm integrity metadata, and declare no
published install lifecycle script. The transitive installed graph is
predominantly MIT (234 package versions), with compatible Apache, ISC, BSD,
Artistic, BlueOak, MPL, CC, Python, and WTFPL terms reviewed in the execution
plan. The two MPL entries are unmodified optional Lightning CSS development
packages; no dependency code or product artifact is distributed. The online
audit reported no known vulnerability.

### CI and dependency updates

GitHub Actions is the CI system. One stable required-check job runs on pull
requests and pushes to `main`, with optional manual dispatch. It has
`contents: read` and no other token permission, no secrets, no
`pull_request_target`, no cache, a bounded timeout, concurrency cancellation,
checkout credential persistence disabled, exact runtime/package-manager
installation, a frozen lockfile, branch/PR-title validation for pull requests,
`verify:ci`, and tracked-worktree drift checks.

Every external action uses a full 40-character commit with a same-line
human-readable release. Node 24 includes
[Corepack](https://github.com/nodejs/corepack), which obtains pnpm from the
exact version and SHA-512 digest in `packageManager`;
`COREPACK_DEFAULT_TO_LATEST=0` prevents an unrelated latest-version lookup.

GitHub's workflow permissions and immutable-action guidance are the primary

### Generated code and artifacts

No generated source code is committed in this phase. TypeScript build output,
coverage, caches, and reports are reproducible ignored artifacts. The committed
pnpm lockfile is machine-generated dependency resolution evidence and is never
hand-edited; its generator is the exact `packageManager` pin and drift is
detected by frozen install plus Git diff.

A future change that commits generated source must document generator,
version, inputs, regeneration command, ownership, review approach, and CI drift
check before adding the artifact.

### Deferred application decisions

This ADR does not select an Agent Skill format, MCP library, transport or
backend framework, schema/validation library for product contracts, API,
database/ORM, vector store, queue/cache/object storage, identity/tenant model,
model provider, telemetry SDK/backend, deployment platform, product scanner,
catalog/ingestion system, retrieval/ranking mechanism, or web framework.

Those choices require concrete product boundaries and later ADRs. Empty API,
MCP, web, backend, package, or database scaffolds are prohibited because they
would create fake ownership and compatibility obligations without current
behavior.

## Consequences

### Benefits

- Contributors receive one exact, reproducible workspace and verification
  contract before product implementation.
- Native Node stripping avoids an extra TypeScript runtime loader for bounded
  local tooling while strict compilation and emitted output preserve type and
  package-boundary correctness.
- Formatting, semantic linting, strict compilation, tests, architecture,
  repository policy, secret detection, and audits have distinct ownership and
  visible failures.
- Default-denied lifecycle scripts, release delay, trust checks, lock
  verification, exact pins, and immutable actions reduce dependency and CI
  supply-chain exposure.
- A real repository-policy package proves the toolchain without inventing
  product services or directories.

### Costs and constraints

- Exact pins and strict supply-chain policy require deliberate, sometimes
  slower dependency updates and registry metadata access during install.
- Typed ESLint, dependency-cruiser, Secretlint, Markdown parsing, coverage, and
  repository checks add development dependencies and CI duration.
- Native-strip-compatible source cannot use transform-required TypeScript
  syntax or runtime path aliases.
- Supporting the minimum Node 24.12 patch constrains dependencies even when a
  contributor uses a newer Node 24 patch.
- GitHub-compatible Markdown anchors have edge cases that require maintained
  fixtures; the tool intentionally does not check external links over the
  network.
- The first coverage result is evidence only, not a regression threshold.

## Rejected alternatives

### Node 26 Current for production

Rejected because Issue #3 selects Node 24 LTS and production workloads should
use the approved LTS line. Node 26 also falls outside the engine contract.

### TypeScript preview, nightly, beta, or RC releases

Rejected because the phase requires stable TypeScript 6.0.x and reproducible
tool compatibility. Prerelease compiler behavior is not a support policy.

### TypeScript 7 or a dual TypeScript 7/6 toolchain in Phase 1

TypeScript 7 is stable and materially faster for many workloads, but 7.0 does
not ship a compiler API. Typed ESLint currently supports the TypeScript 6 API
line through `<6.1.0`. Running TypeScript 7 beside the TypeScript 6
compatibility/API package would preserve typed linting, but the extra compiler,
aliases, commands, and failure modes have no measured value for this single
tooling package. The repository remains on TypeScript 6.0.3 until the API and
tooling transition is supportable or measured compiler performance justifies a
dual-toolchain migration.

### npm or Yarn as the initial package manager

Rejected because pnpm 11 provides the approved workspace model and explicit
release-age, trust, exotic-source, lock verification, peer, engine, and build
controls. Supporting multiple managers would create competing lock/install
contracts.

### A separate pnpm setup action

Rejected after hosted validation because the selected Node 24 line already
includes Corepack and the repository's integrity-bound `packageManager` field
is sufficient. The initial `pnpm/action-setup@v6.0.9` run added an unnecessary
self-installer boundary and emitted a high-severity npm audit warning before
switching to the selected pnpm version. Corepack removes that external action
and its bootstrap graph.

### CommonJS for new owned code

Rejected because ESM and NodeNext align with modern Node and the selected tool
ecosystem. Mixed module semantics would add interop complexity without a
current consumer.

### A task runner before measured need

Turborepo, Nx, Bazel, and similar systems are rejected. One private package and
root scripts do not justify another orchestration layer or cache trust
boundary.

### Combining formatting and semantic lint rules

Rejected because competing format rules create duplicate ownership and noisy
failures. Prettier formats; ESLint enforces semantics; the compatibility config
disables conflicts.

### Git hooks as the only enforcement mechanism

Rejected because hooks are local, bypassable, and environment-dependent.
Documented commands and CI are authoritative. Mandatory Husky or another hook
manager is outside scope.

### Custom YAML or Markdown parsing

Rejected because workflow structure and CommonMark links/headings have security
and compatibility edge cases. Focused established parsers are safer than
regex-only parsing, subject to explicit resource bounds and dependency review.

### Scaffolding empty API, MCP, web, backend, package, or database applications

Rejected because placeholder directories imply architecture and ownership
without executable behavior. Workspace globs reserve future locations without
fake implementations.

### Trusting the lockfile to skip supply-chain verification

Rejected because an attacker may author a lockfile under weaker policy.
`trustLockfile` remains false even though the lockfile is committed and frozen.

### Globally allowing dependency builds

Rejected because current or future transitive packages could execute new
lifecycle code. Builds are denied by default and approved only by reviewed
exact package/version need.

### CodeQL or GitHub dependency-review action

Rejected because Issue #3 states the private personal repository lacks the
required GitHub Code Security entitlement and explicitly excludes them. Local
Secretlint, pnpm audit, exact pins, and review provide this phase's available
controls.

## Revisit triggers

Revisit through a new or superseding ADR when a measurable condition occurs:

- Node 24 enters end-of-life or a security/support requirement establishes a
  date to move the minimum supported major.
- TypeScript, typescript-eslint, Vitest, dependency-cruiser, Secretlint, or
  another required tool drops compatibility with the supported Node/TypeScript
  line and no maintained patch exists.
- `typescript-eslint` officially supports the TypeScript 7 toolchain and its
  required compiler API.
- TypeScript 7.1 or later provides the compiler API required by GitBlocks'
  typed linting and related tooling.
- In 20 comparable local or CI runs, TypeScript compilation is at least 30% of
  the verification critical path and a reviewed TypeScript 7 or dual-toolchain
  prototype reduces that path by at least 25% without weakening typed linting,
  reproducibility, or supply-chain controls.
- Native TypeScript tooling requires non-erasable syntax or its direct-source
  startup/diagnostic cost exceeds emitted-tool execution by at least 20% in
  repeatable CI measurements.
- The workspace reaches at least 10 active packages, or the verification
  critical path exceeds 10 minutes in the median of 20 comparable CI runs, and
  a task runner prototype demonstrates at least a 30% reduction without
  weakening reproducibility or cache security.
- The dependency graph or install verification exceeds 1 GiB peak memory or 5
  minutes in the median of 20 clean CI installs and a proposed policy change
  includes equivalent trust evidence.
- External-link correctness becomes a repeated release defect (at least three
  independently confirmed broken external links in two months), justifying a
  separately bounded, cached, retry-aware network validation design.
- A representative coverage baseline and critical-module review approve an
  explicit threshold/ratchet issue under the testing strategy.
- A real application/package boundary requires a framework, contract schema,
  telemetry, deployment, or generated-code decision currently deferred here.

Preference, novelty, a new major release alone, or isolated CI inconvenience is
not a revisit trigger.
